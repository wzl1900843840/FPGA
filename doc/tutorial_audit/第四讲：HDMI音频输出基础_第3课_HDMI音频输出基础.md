## 二、HDMI音频输出的核心概念

### 2.1 I2S协议基础

I2S（Inter-IC Sound）是飞利浦公司制定的音频串行总线标准，用于在芯片之间传输数字音频数据。

**I2S接口有3根信号线**：

| 信号 | 名称 | 说明 |
|------|------|------|
| BCLK | 位时钟（Bit Clock） | 每一位数据对应一个BCLK周期 |
| LRCK | 左右声道时钟（Left/Right Clock） | 0=左声道，1=右声道，频率=采样率 |
| DOUT | 串行数据（Data Out） | 高位在先，MSB First |

**64fs时序**：fs是采样率（48kHz），64fs表示BCLK频率=64×48kHz=3.072MHz。为什么是64？因为一个采样帧每个声道占用32个BCLK周期（24位数据+8位填充），左右声道合计64个BCLK周期。

[代码/图示块另行核对]

> **图注**：I2S 64fs采样帧结构——一个采样帧=左声道24位+填充8位+右声道24位+填充8位=64个BCLK周期。关键信号：BCLK=3.072MHz（64×48kHz）、LRCK=48kHz（fs）、DOUT。结论：64fs是HDMI音频最常用格式，左右声道各占32个BCLK周期。

**数据格式**：高位在先（MSB First），24位有符号整数，左声道在LRCK=0时传输，右声道在LRCK=1时传输。

### 2.2 音频时钟与采样率

**48kHz采样率**是什么意思？每秒采集48000个音频样本。每个样本24位（官方例程）或16位（完赛工程）。

**音频时钟体系**：

[代码/图示块另行核对]

> **图注**：音频时钟体系——50MHz系统时钟→PLL生成12.288MHz→÷4得BCLK 3.072MHz（64fs）→÷64得LRCK 48kHz（fs）。关键：12.288MHz=256×48kHz，是48kHz音频的标准母钟。结论：音频时钟必须从独立PLL生成（官方例程），完赛工程改为复用像素时钟。


- **12.288MHz**：音频主时钟（MCLK），256fs（256×48kHz=12.288MHz）
- **3.072MHz**：位时钟（BCLK），64fs
- **48kHz**：采样率（LRCK），fs

为什么用12.288MHz而不是直接用48kHz？因为12.288MHz = 256 × 48kHz，是音频系统的标准主时钟（MCLK），能同时生成BCLK（3.072MHz，64fs）和LRCK（48kHz，fs），且与视频像素时钟之间通过ACR包建立精确关系。

### 2.3 正弦波生成（DDS原理）

官方例程用的是方波，音质差。更好的方式是用**DDS（直接数字频率合成）**生成正弦波。

**DDS原理**：用一个相位累加器，每个采样周期加上一个相位增量，然后用相位值去查正弦波查找表（LUT），得到正弦波样本。

### 2.4 HDMI音频包封装基础

I2S输出的是原始音频样本，HDMI传输的是数据包。音频样本需要封装成HDMI音频包才能通过HDMI传输。

**HDMI音频包类型**：

| 包类型 | 说明 |
|--------|------|
| 音频采样包（Audio Sample Packet） | 承载实际的音频样本数据 |
| 音频InfoFrame包 | 描述音频格式（采样率、位深、声道数等） |
| ACR包（Audio Clock Regeneration） | 音频时钟再生，让接收端恢复音频时钟 |

[代码/图示块另行核对]

> **图注**：HDMI音频包封装流程——PCM音频样本→音频采样包封装（Packet Header+SubPacket0~3）→InfoFrame/ACR→TMDS编码（Transition Minimized Differential Signaling，最小化跳变差分信号）→HDMI发射器。关键：HDMI音频不是直接输出I2S，而是封装成音频包随视频消隐期传输。结论：理解音频包封装是实现HDMI音频的核心，ACR用于音视频同步。

**完赛工程的实现**：`hdmi_audio_symbol_core.v`负责把PCM样本封装成HDMI音频符号，内部包含了音频采样包封装、InfoFrame包封装、ACR包封装。这个模块比较复杂，但接口很简单：输入PCM样本，输出HDMI符号（channel0/1/2_symbol）。

### 2.5 音视频同步基础

**音视频同步**是什么？就是音频和视频在时间上对齐，不会出现"声音先到"或"画面先到"的情况。

**HDMI音视频同步的原理**：

- 视频有自己的时钟（pixel_clk，25MHz@640×480@60Hz）
- 音频有自己的时钟（12.288MHz）
- 两个时钟是独立的，频率不同
- HDMI通过**ACR包**（Audio Clock Regeneration）告诉接收端音频时钟和视频时钟的关系，接收端根据这个关系恢复音频时钟

## 三、从官方到完赛的过渡思路

### 3.1 整体架构对比

[代码/图示块另行核对]

> **图注**：官方与完赛音频链路对比——官方：音频PLL→方波+I2S→HDMI发射器；完赛：像素时钟(25MHz)→正弦波生成(16点LUT)→PCM契约适配→音频包封装→HDMI发射器。关键：完赛工程复用视频像素时钟，不需要独立音频PLL。结论：从方波到正弦波、从独立PLL到复用像素时钟，是第3课的核心升级。


**核心差异**：
1. **时钟**：官方用独立的12.288MHz音频PLL，完赛复用25MHz像素时钟（通过分频生成48kHz采样脉冲）
2. **波形**：官方用方波（相位累加器），完赛用正弦波（16点LUT）
3. **接口**：官方输出I2S，完赛输出HDMI符号（直接封装音频包）
4. **音频包封装**：官方依赖HDMI发射器内部封装，完赛自己封装（hdmi_audio_symbol_core）

### 3.2 pcm_test_tone 模块详解

完赛工程的测试音生成模块是`pcm_test_tone.v`（约74行），比官方例程简洁很多。

**端口分类**：

| 信号 | 方向 | 说明 |
|------|------|------|
| clk / rst_n | 输入 | 时钟/复位（用像素时钟25MHz） |
| enable | 输入 | 使能 |
| sample_valid / sample_ready | 输出/输入 | 样本有效/下游就绪 |
| sample_left / sample_right | 输出 | 左/右声道16位样本 |
| rom_index | 输出 | 当前LUT索引（调试用） |

**核心逻辑**：

[代码/图示块另行核对]

> **图注**：pcm_test_tone数据流——分频计数(div_count 0~999，25MHz/1000=25kHz，如需48kHz应设SAMPLE_DIV≈521)→输出样本(sample_valid=1)→LUT索引递增(rom_index 0~15循环)→回到分频计数。关键：这是数据流不是状态机，用分频器+LUT实现正弦波。结论：pcm_test_tone是最简单的音频源，用于验证HDMI音频通路。



**代码逻辑四步拆解：**

**第一步，分频计数。** `div_count`从0加到`SAMPLE_DIV-1`（999），加到999就清零。这样每1000个时钟周期产生一个分频脉冲。

**第二步，输出样本。** 当`div_count==999`且`sample_valid==0`时，从`sine_sample(rom_index)`取值，赋给`sample_left`和`sample_right`，`sample_valid`置1。

**第三步，握手机制。** 当`sample_valid && sample_ready`时（样本被下游接收），`sample_valid`清零，`rom_index`加1。这样就实现了valid/ready握手机制，上游不会覆盖未被接收的样本。

**第四步，rom_index循环。** `rom_index`是4位寄存器，从0加到15，加到15后再加1就溢出回到0，自动循环。这样16点LUT就循环寻址，生成连续的正弦波。

**频率计算：**

- 当前`SAMPLE_DIV=1000`，25MHz/1000=25kHz采样率
- `rom_index`每样本加1，16个样本一个周期，所以输出频率=25kHz/16=**1562.5Hz**
- 如果要48kHz采样率，`SAMPLE_DIV`应该设为25000000/48000≈**521**，输出频率=48kHz/16=**3kHz**
- 如果要440Hz，需要每48000/440≈109个样本一个周期，16点LUT的话每109/16≈6.8个样本rom_index加1，这就需要更复杂的相位累加器了。但测试音用固定频率完全够用。

3. **媒体音调联动**：media_id控制音调，切换图片时音调变化，演示效果好

## 六、常见问题与调试技巧

### Q1：没有声音输出

**排查步骤**：
1. 检查audio_bridge的enable是否为1
2. 检查sample_valid是否有脉冲（用ILA抓，应该是48kHz）
3. 检查sample_left/sample_right是否有数据（不是全0）
4. 检查HDMI符号输出是否正常（channel0/1/2_symbol是否在变化）
5. 检查显示器是否支持音频（有些显示器没有扬声器）
6. 检查HDMI线是否支持音频（有些劣质HDMI线只接了视频引脚）

### Q2：声音有杂音/爆音

**可能原因**：
1. 采样率不匹配（应该是48kHz，实际是其他频率）
2. 音频幅值过大（超过16位有符号范围，导致削波）
3. 时钟不稳定（像素时钟有抖动，导致音频采样率不稳定）
4. HDMI音频包封装时序错误（样本没有正确封装到包里）

**解决方法**：
1. 用ILA抓sample_valid，测量频率是否为48kHz
2. 检查sample_left/sample_right的幅值，不要超过±20000
3. 检查PLL配置，确保像素时钟稳定
4. 参考完赛工程的hdmi_audio_symbol_core，不要自己写音频包封装

### Q3：音视频不同步

**可能原因**：
1. ACR包的N/CTS值错误，接收端无法正确恢复音频时钟
2. 音频缓冲过大或过小，导致音频延迟
3. 视频和音频的启动时间不同步

**解决方法**：
1. 完赛工程的hdmi_audio_symbol_core会自动计算N/CTS，不要手动修改
2. 音频延迟通常在几十毫秒以内，人耳很难察觉，不需要特别处理
3. 确保上电时视频和音频同时启动

### Q4：切换图片时音调没有变化

**可能原因**：
1. media_id没有正确接到audio_bridge
2. pcm_media_tone的media_id到频率的映射有问题
3. 音调变化太快，人耳听不出来

**解决方法**：
1. 用ILA抓media_id，确认切换图片时media_id在变化
2. 检查pcm_media_tone的note_inc_lut，确认每个media_id对应不同的频率
3. 可以增大每个音调的持续时间，或者用差异更大的频率
