## 一、官方例程 bmp_read.v 深度拆解

`bmp_read.v`是BMP文件的解析和读取模块，负责两件事：①上电时扫描TF卡，找出前4张BMP文件的起始扇区；②按指定扇区加载一张BMP的像素数据到SDRAM。官方例程中这个文件约320行代码，5个状态。

### 1.1 模块接口

[代码/图示块另行核对]

**接口解读：**
- 两组主要接口：扫描接口（找BMP文件）和加载接口（读BMP像素）
- SD卡接口是按扇区读的——一次读512字节，`sd_sec_read_data_valid`表示数据有效，`sd_sec_read_end`表示整个扇区读完
- 像素数据输出是24位RGB888，3个字节组成一个像素（B→G→R顺序）

### 1.2 五个状态的状态机


**图3-1 bmp_read核心状态机：**

[代码/图示块另行核对]

> **图例：**
> - `header_match`：BMP头校验是否通过（签名/尺寸/位深/压缩方式等6项检查）
> - `file_len`：BMP文件总字节数（从文件头偏移2-5读取）
> - `bmp_len_cnt`：当前已读取的字节计数器，达到`file_len`表示整帧读完
> - **完成条件**：扇区读完且（找到目标数量 或 扫到最大扇区）
> - **未找到**：扇区读完且未匹配BMP头，继续下一扇区

**五个状态的功能：**
- `ST_IDLE`(0)：空闲状态，等待scan_start或load_start
- `ST_SCAN`(1)：扫描状态，逐个扇区读，检查BMP头
- `ST_LOAD_HDR`(2)：加载头状态，读BMP文件的第一个扇区（512字节），解析并校验头
- `ST_LOAD_WAIT`(3)：等待写应答状态，向SDRAM控制器发写请求，等应答
- `ST_LOAD_DATA`(4)：加载数据状态，逐个扇区读BMP像素数据，3字节组成一个像素输出

### 1.3 BMP头解析与校验

官方例程解析BMP头的前54个字节（标准BMP头大小），存在对应的寄存器里：

| 偏移 | 字段 | 位宽 | 寄存器 | 说明 |
|---|---|---|---|---|
| 0-1 | 签名 | 16bit | header_0, header_1 | "BM"（0x42 0x4D） |
| 2-5 | 文件大小 | 32bit | file_len | 整个BMP文件的字节数 |
| 6-9 | 保留 | 32bit | - | 必须为0，官方没检查（不重要） |
| 10-13 | 像素偏移 | 32bit | pixel_offset | 像素数据从文件第几个字节开始（默认54） |
| 14-17 | DIB头大小 | 32bit | - | 必须>=40，官方没检查 |
| 18-21 | 宽度 | 32bit | width | 图片宽度（像素） |
| 22-25 | 高度 | 32bit | height | 图片高度（像素，正=bottom-up，负=top-down） |
| 26-27 | 平面数 | 16bit | - | 必须为1，官方没检查 |
| 28-29 | 位深 | 16bit | bit_count | 每像素位数（必须24） |
| 30-33 | 压缩方式 | 32bit | compression | 必须为0（不压缩） |

**官方只检查了6项，漏掉了4项重要检查（还有1项保留字段检查不重要）：**

### 1.4 扫描逻辑

扫描时从`scan_start_sector`开始，逐个扇区读，每个扇区读完后检查`header_match`：


**图3-2 BMP扫描流程图：**

[代码/图示块另行核对]

> **图例：**
> - **跳整文件**：当前扇区是BMP文件头但校验失败（如尺寸不对），直接跳到下一个文件
> - **跳1扇区**：当前扇区不是BMP文件头，逐个扇区往后找
> - `file_sector_count = (file_len + 511) >> 9`：文件大小向上取整到512字节的倍数（跳整文件时按此计算）

**扫描逻辑的关键细节：**
- 匹配时跳`file_sector_count`个扇区（整个文件大小对应的扇区数），因为这是一个BMP文件，下一个文件肯定在它后面
- 不匹配时只跳1个扇区——这是官方扫描效率低的原因，如果卡上有很多非BMP文件（比如音频、文档），会一个扇区一个扇区地跳过，很慢
- `file_sector_count = (file_len + 511) >> 9`，即文件大小向上取整到512字节的倍数

### 1.5 加载逻辑

加载一张BMP分三步：
1. **ST_LOAD_HDR**：读BMP的第一个扇区（512字节），解析头，校验`header_match`。校验通过→发写请求→ST_LOAD_WAIT；校验失败→直接回ST_IDLE（**没有错误码上报！**）
2. **ST_LOAD_WAIT**：等SDRAM控制器的`write_req_ack`，收到后→ST_LOAD_DATA
3. **ST_LOAD_DATA**：从第一个扇区开始，逐个扇区读，`bmp_len_cnt`计数已读字节数。当`bmp_len_cnt >= pixel_offset`且`< file_len`时，数据是有效像素，3个字节组成一个24位像素输出。读完整个文件（`bmp_len_cnt >= file_len`）→回ST_IDLE

## 二、7项稳定性优化实现

### 2.1 BMP严格校验（必做）

**问题：** 官方只查6项，漏了DIB头大小、平面数、pixel_offset范围、file_len合理性4项重要检查。

**改动：**
1. 新增2个寄存器：`dib_size`（偏移14-17）、`planes`（偏移26-27）
2. 在BMP头解析case中新增2个字段的存储
3. `header_match`条件新增5个校验项

**完整的严格校验条件：**

[代码/图示块另行核对]

**为什么这5项重要：**
- `dib_size>=40`：防止伪造的BMP头（DIB头最小40字节）
- `planes==1`：BMP标准要求平面数必须为1，不为1说明不是标准BMP
- `pixel_offset范围`：防止像素偏移指向文件外或头区域，导致读越界
- `file_len合理性`：防止文件大小不够装下所有像素，导致截断

### 2.2 错误码上报与恢复（必做）

**问题：** 官方校验失败直接回IDLE，上层不知道发生了什么，会一直等。

**改动（bmp_read.v）：**

1. 新增2个输出端口：`bmp_error[2:0]`（错误码）、`load_error`（加载失败脉冲）
2. 定义4个错误码：
   - `ERR_NONE = 3'd0`：无错误
   - `ERR_HEADER = 3'd1`：BMP头校验失败
   - `ERR_TIMEOUT = 3'd2`：SD卡读取超时
   - `ERR_TRUNCATED = 3'd3`：像素数据截断（不完整）
3. 在ST_LOAD_HDR状态，校验失败时输出`bmp_error=ERR_HEADER`和`load_error=1`，然后回IDLE

**改动（sd_card_bmp.v）：**

1. 新增2个寄存器：`load_error_seen`（检测到错误）、`retry_count`（重试次数）
2. 复位时初始化`load_error_seen=0`、`retry_count=0`
3. 3个加载启动分支（首图/手动/自动）都清零`load_error_seen`和`retry_count`
4. 加载完成分支（正常完成）清零`load_error_seen`和`retry_count`
5. always块最前面新增错误恢复逻辑：
[代码/图示块另行核对]

**恢复策略：重试1次→失败跳过→保留上一帧**

- 第一次加载失败：自动重试1次（可能是SD卡瞬时错误）
- 重试仍失败：跳过这张坏图，保持显示上一张正常图
- 上层（sd_card_bmp.v）知道发生了错误，可以在数码管或OSD上提示

### 2.3 坏图快速跳过（必做）

**问题：** 官方扫描时不匹配只跳1个扇区，卡上文件多时扫描极慢。

**改动（bmp_read.v ST_SCAN状态）：**

官方逻辑：不匹配→`scan_sector += 1`（只跳1个扇区）

优化逻辑：不匹配时，先检查当前扇区的前2字节是不是"BM"：
- 如果是"BM"：说明可能是一个BMP文件头，但校验失败（尺寸不对/位深不对等），根据`file_len`快速跳过整个文件：`scan_sector += file_sector_count`
- 如果不是"BM"：说明不是BMP文件头，继续跳1个扇区：`scan_sector += 1`

[代码/图示块另行核对]

**效果：** 卡上有很多大文件（比如音频、视频）时，扫描速度提升几十倍。原来扫一张坏图要几秒，现在只要几毫秒。

### 2.4 加载超时（必做）

**问题：** 官方没有超时机制，SD卡读卡住时状态机一直等，死锁。

**改动（bmp_read.v）：**

1. 新增2个参数：`SD_READ_TIMEOUT_MS`（超时时间，默认500ms）、`CLK_FREQ_HZ`（时钟频率，默认100MHz）
2. 新增1个寄存器：`sd_timeout_cnt`（超时计数器）
3. 进入ST_SCAN和ST_LOAD_DATA状态时，清零`sd_timeout_cnt`
4. 在ST_SCAN和ST_LOAD_DATA状态中，每个时钟周期`sd_timeout_cnt += 1`
5. 当`sd_timeout_cnt >= SD_READ_TIMEOUT_MS * CLK_FREQ_HZ / 1000`时，判定超时：
   - 输出`bmp_error=ERR_TIMEOUT`和`load_error=1`
   - 回ST_IDLE

[代码/图示块另行核对]

**为什么500ms合适：** 正常读一个扇区（512字节）在100MHz下约几毫秒，500ms是正常时间的100倍，足够应对SD卡的瞬时延迟，但不会等太久。

### 2.5 像素完整性校验（必做）

**问题：** 官方`bmp_len_cnt>=file_len`就认为完成，不检查实际输出了多少像素。截断的BMP会显示半帧旧图半帧新图（撕裂）。

**改动（bmp_read.v）：**

1. 新增1个寄存器：`pixel_count`（已输出像素数）
2. 进入ST_LOAD_HDR状态时，清零`pixel_count`
3. 在ST_LOAD_DATA状态中，每次输出一个像素（`bmp_data_wr_en=1`）时，`pixel_count += 1`
4. 加载完成时（`bmp_len_cnt >= file_len`），检查`pixel_count`是否等于期望像素数：
   - 期望像素数 = `bmp_width * bmp_height` = 640 * 480 = 307200
   - 如果`pixel_count < 307200`：说明像素数据截断，输出`bmp_error=ERR_TRUNCATED`和`load_error=1`
   - 如果`pixel_count == 307200`：正常完成，回ST_IDLE

[代码/图示块另行核对]

**为什么需要这个检查：** BMP文件可能被截断（拷贝中断、文件系统损坏），文件大小字段可能是完整的，但实际像素数据不够。如果不检查，SDRAM中会有一部分是旧图的像素，一部分是新图的像素，显示时出现撕裂。检查后，截断的图会被判定为错误，触发重试或跳过，保持显示上一张完整图。

### 2.7 快速启动（选做）

**问题：** 官方必须等4张图全扫完才开始显示首图，上电后要等几秒。

**改动思路（参考完赛工程fast_boot_gate）：**

1. 扫描时，找到第一张BMP就立即启动加载，不等剩下的3张
2. 显示首图的同时，后台继续扫描剩下的3张
3. 用一个"快速启动门控"信号控制：首图就绪→立即播放；后续图片扫描完成→更新图片索引表

**感知启动时间：** 从4秒（等4张全扫完）降到1秒（只等第1张扫完+加载）。

这个优化改动稍大，涉及扫描和显示的并行控制，建议在完赛工程中参考实现，基础完赛可以不做。

### 2.11 BMP解码器独立化（从bmp_read到bmp24_decoder）

官方例程的`bmp_read.v`是一个**all-in-one模块**：既负责SD卡扇区扫描，又负责BMP头解析，还负责像素数据输出。完赛工程把BMP解码**独立成单独模块**`bmp24_decoder.v`，和文件系统层解耦。

**官方bmp_read的问题**：

1. **职责不清**：扇区扫描+BMP解析+像素输出混在一起，修改一个功能可能影响其他
2. **耦合严重**：直接和sd_card_top对接，换存储介质（如eMMC）要重写整个模块
3. **难以测试**：必须配合SD卡才能测试BMP解析，无法单独写Testbench
4. **错误码不清晰**：BMP校验失败和SD卡读失败混在一起，无法区分

**完赛bmp24_decoder的设计**：

**核心改进**：
1. **输入是字节流**：`file_valid/file_byte/file_byte_offset`，不关心数据来自SD卡还是其他存储
2. **输出是像素流**：`pixel_valid/pixel_rgb/pixel_x/pixel_y`，不关心像素写到哪里
3. **独立错误码**：8种BMP-specific错误（签名错/尺寸错/位深错/压缩错/截断等）
4. **可单独测试**：Testbench直接喂字节流，不需要SD卡

基础版（2.2节）用3位错误码，只区分4类错误；完赛工程把错误码扩展为8位，细分为8种，便于定位具体问题。

**8种BMP错误码**：
| 错误码 | 含义 |
|--------|------|
| 0x31 | ERR_SIGNATURE：不是"BM"签名 |
| 0x32 | ERR_DIMENSIONS：尺寸不是640×480 |
| 0x33 | ERR_PLANES：planes不是1 |
| 0x34 | ERR_BPP：位深不是24 |
| 0x35 | ERR_COMPRESSION：有压缩（BI_RLE） |

| 0x37 | ERR_TRUNCATED：文件截断，像素不完整 |
| 0x38 | ERR_UPSTREAM：上游（文件系统）错误 |

## 核心知识总结

**本节课你应该记住的5个关键点：**

1. **BMP严格校验是稳定性的第一道防线**——官方只查6项，漏掉的DIB头大小、平面数、pixel_offset范围、file_len合理性这4项，每一项都可能导致坏图通过校验。严格校验后，坏图在源头就被拦截了。

2. **错误码上报+重试+跳过是标准的错误恢复三段式**——出错时先上报错误码（让上层知道），然后重试1次（应对瞬时错误），重试失败再跳过（应对持久错误），全程保留上一帧（不花屏）。这个模式在FPGA设计中非常通用。

3. **超时机制是防止死锁的最后一道保险**——SD卡、SDRAM、HDMI这些外部设备都可能卡住，没有超时机制的状态机会一直等，必须重启。加一个500ms的超时计数器，进入状态时清零，超时就退出，简单有效。

4. **像素完整性校验能防止撕裂**——`bmp_len_cnt>=file_len`只说明文件读完了，不说明像素够了。截断的BMP文件大小字段可能是完整的，但实际像素数据不够。用`pixel_count`计数实际输出的像素数，完成时检查是否等于307200（640x480），就能发现截断。

5. **从官方到完赛的演进是"最小改动→模块拆分→完整架构"三步走**——不要一上来就做完整架构，先在官方基础上改100多行做5项必做优化，确保能跑、稳定。然后再把校验和恢复抽成独立模块，最后加上可观测性。循序渐进，每一步都能验证。
