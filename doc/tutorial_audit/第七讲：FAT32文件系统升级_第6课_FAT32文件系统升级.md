## 一、官方例程的TF卡读取方式与局限

### 1.1 官方读取方式深度拆解

官方例程的TF卡读取由两个模块完成：`sd_card_top`（SD卡底层驱动，初始化+扇区读写）和`bmp_read`（BMP扫描+加载）。

**核心方式：直接读物理扇区，通过BMP魔数扫描**

[代码/图示块另行核对]

**关键参数（sd_card_bmp.v的parameter）：**

- `SCAN_START_SECTOR = 32'd0`：从扇区0开始扫描
- `SCAN_MAX_SECTOR = 32'd131071`：最多扫到扇区131071（约64MB位置）
- `SCAN_TARGET_COUNT = 3'd4`：找前4张BMP

**扫描原理**：bmp_read从扇区0开始，逐个扇区读取，检查每个扇区的前两个字节是不是`0x42 0x4D`（ASCII的"BM"，BMP文件的魔数）。如果是，就认为这个扇区是一个BMP文件的起始位置，记录下来。找到4个就停止扫描。

**加载原理**：加载图片时，从记录的起始扇区开始，连续读取扇区——先读BMP文件头（解析宽高、位深、数据偏移），然后按顺序读像素数据，直接送到SDRAM。

### 1.2 官方方式的5个严重局限

把官方读取方式彻底搞懂之后，我们能发现5个严重局限：

[代码/图示块另行核对]

> **Note：** ①官方只认"BM"魔数，不认识FAT32文件系统，不知道文件名和目录结构；②不支持碎片化文件，文件不连续存放就读取错误；③默认只扫前64MB，大卡后面的图片扫不到；④只能扫根目录下连续存放的文件，不支持子目录；⑤其他文件内容里有"BM"会被误判为BMP文件。

**逐个说明：**

1. **不认识文件系统**：官方例程完全不知道FAT32是什么，它直接读物理扇区，靠"BM"魔数判断BMP文件。它不知道文件名、不知道目录结构、不知道文件大小、不知道文件存在哪个簇里。这就像你在图书馆里不看书目索引，直接一本书一本书翻，看封面有没有"图片"两个字——效率极低，而且很容易错。

2. **不支持碎片化文件**：官方加载时从起始扇区开始**连续读扇区**，假设BMP文件是连续存放的。但实际上，TF卡用久了之后，文件系统会把文件分散存放在不同的簇里（碎片化）。如果BMP文件不连续，官方读到中间就会读到其他文件的数据或者空闲扇区，导致图片加载错误、花屏。你把TF卡插到电脑上拷文件，文件系统可能把文件放在任何位置，不保证连续。

3. **扫描范围有限**：`SCAN_MAX_SECTOR = 131071`，也就是最多扫到扇区131071。131072个扇区 × 512字节 = 64MB。也就是说，官方例程只扫描TF卡前64MB的范围。如果你的BMP文件存在64MB之后的位置（比如TF卡是8GB/32GB的，文件存在后面），官方例程根本扫不到。而且这个参数是编译时固定的，不能动态适配不同容量的TF卡。

4. **不支持子目录**：官方例程只扫描物理扇区，不解析目录项，所以它不知道什么是子目录。如果你的BMP文件存在子目录里（比如`/photos/pic1.bmp`），官方例程扫到目录项扇区时，目录项里可能恰好有"BM"两个字节（比如文件名里有B和M），会被误判；但真正的图片数据在子目录对应的簇里，官方根本找不到。

5. **容易误判**：官方只靠前两个字节"BM"判断BMP文件。但其他文件的内容里、目录项里、甚至空闲扇区的残留数据里，都可能恰好有`0x42 0x4D`这两个字节。这时候官方会误判为BMP文件，记录错误的起始扇区，加载时就会读错数据、花屏、甚至卡死。而且BMP文件本身也可能不是从扇区边界开始的（如果文件系统把文件放在簇中间），但官方假设每个BMP都从扇区边界开始，这也是一个隐含的错误假设。

这5个局限，就是本节课要解决的。解决方案就是：**引入FAT32文件系统**，让FPGA真正"认识"TF卡的文件系统，通过目录项找文件，通过FAT链读文件，而不是靠魔数在物理扇区里瞎扫。

## 二、FAT32文件系统基础

在讲怎么改之前，我们先把FAT32的核心概念搞清楚。这部分是基础，理解了这些，后面的代码就很容易懂了。

### 2.1 FAT32的核心概念

[代码/图示块另行核对]

**1. MBR（Master Boot Record，主引导记录）**

- 位于TF卡的LBA0（第一个扇区）
- 包含分区表：记录TF卡上有几个分区，每个分区的类型、起始扇区、大小
- FAT32分区的类型码通常是`0x0B`或`0x0C`
- 也可以没有MBR，直接把TF卡整个作为一个FAT32分区（称为"超级软盘"格式，引导扇区直接在LBA0）
- 关键：要先读LBA0，判断是MBR还是直接引导扇区，然后找到FAT32分区的起始位置   

**2. 引导扇区（Boot Sector）和BPB（BIOS Parameter Block）**

- 位于FAT32分区的第一个扇区
- 包含文件系统的所有关键参数，称为BPB
- 关键参数：
  - `bytes_per_sector`（偏移11，2字节）：每扇区字节数，通常512
  - `sectors_per_cluster`（偏移13，1字节）：每簇扇区数，通常1/2/4/8/16/32
  - `reserved_sectors`（偏移14，2字节）：保留扇区数，通常32
  - `fat_count`（偏移16，1字节）：FAT表数量，通常2
  - `total_sectors`（偏移32，4字节）：分区总扇区数
  - `fat_sectors`（偏移36，4字节）：每个FAT表的扇区数
  - `root_cluster`（偏移44，4字节）：根目录起始簇号，通常是2
- 引导扇区的最后两个字节必须是`0x55 0xAA`（引导签名） 

**3. FAT表（File Allocation Table，文件分配表）**

- 位于保留区之后
- 每个簇在FAT表中有一个4字节的条目（FAT32用4字节，FAT16用2字节，FAT12用1.5字节）
- FAT条目的值表示：
  - `0x0000000`：空闲簇
  - `0x0000002 ~ 0x0FFFFFEF`：下一个簇的簇号（FAT链）
  - `0x0FFFFFF8 ~ 0x0FFFFFFF`：文件结束（EOF）
  - `0x0FFFFFF7`：坏簇
- 通常有2个FAT表（fat_count=2），互为备份
- 关键作用：通过FAT链找到文件的所有簇，支持碎片化文件

**4. 数据区（Data Region）**

- 位于FAT表之后
- 根目录从簇2开始（FAT32的根目录不再是固定区域，而是存在数据区的簇链里）
- 数据区的每个簇都有一个编号，从2开始（簇0和簇1是保留的，簇0是FAT表的起始标记，簇1是保留簇）
- 文件数据存在簇里，一个文件可以占多个簇，通过FAT链连接

**5. 目录项（Directory Entry）**

- 目录是一个特殊的文件，内容是一系列32字节的目录项
- 每个目录项描述一个文件或子目录：
  - 文件名（偏移0，8字节）：8.3格式的主文件名，不足8字节用空格填充
  - 扩展名（偏移8，3字节）：3字节扩展名，不足用空格填充
  - 属性（偏移11，1字节）：只读/隐藏/系统/卷标/子目录/归档
  - 起始簇号高16位（偏移20，2字节）
  - 起始簇号低16位（偏移26，2字节）
  - 文件大小（偏移28，4字节）
- 例如`PIC1.BMP`的目录项：文件名是`PIC1    `（PIC1+4个空格），扩展名是`BMP`

### 2.3 FAT链的遍历原理

FAT链是FAT32最核心的机制，也是解决"碎片化文件"问题的关键。

[代码/图示块另行核对]

**遍历过程：**
1. 从目录项拿到文件的起始簇号（first_cluster）
2. 读取该簇的所有扇区，输出文件数据
3. 该簇读完后，去FAT表查这个簇对应的FAT条目，得到下一个簇号
4. 如果下一个簇号是`0x0FFFFFF8 ~ 0x0FFFFFFF`，表示文件结束，停止
5. 否则，读取下一个簇的数据，重复步骤3-4

**FAT条目的定位方法（关键）：**

每个FAT条目4字节，每个扇区512字节，所以每个扇区有 `512 / 4 = 128` 个FAT条目。

[代码/图示块另行核对]

- `cluster_number >> 7`：簇号除以128，得到FAT表内的扇区号
- `cluster_number & 0x7F`：簇号对128取余，得到扇区内的条目索引
- `<< 2`：每个条目4字节，乘以4得到字节偏移

例如：簇号5 → fat_sector = fat_start_lba + 0，fat_offset = 5 × 4 = 20（扇区内第20字节开始的4字节就是FAT[5]）

**为什么FAT链能解决碎片化问题？** 因为不管文件的簇在磁盘上怎么分散，FAT链都能按顺序把它们串起来。读取时按FAT链一个簇一个簇读，就能得到完整的文件内容，不需要文件连续存放。

### 2.4 SD卡SPI底层协议

FAT32文件系统运行在SD卡之上，理解SD卡的SPI协议是调试存储问题的基础。

**SD卡SPI模式的引脚**：
| 引脚 | 名称 | 方向 | 说明 |
|------|------|------|------|
| 1 | CS | 主机→卡 | 片选，低有效 |
| 2 | MOSI | 主机→卡 | 主出从入，数据输入 |
| 3 | GND | - | 地 |
| 4 | VCC | - | 3.3V电源 |
| 5 | SCLK | 主机→卡 | SPI时钟 |
| 6 | GND | - | 地 |
| 7 | MISO | 卡→主机 | 主入从出，数据输出 |

**SD卡初始化流程（SPI模式）**：
1. **上电延时**：等待100ms，让SD卡电源稳定
2. **发送74个时钟**：CS=高，MOSI=1，发送至少74个时钟周期，让SD卡进入SPI模式
3. **CMD0（GO_IDLE_STATE）**：复位SD卡，进入空闲状态，返回R1=0x01
4. **CMD8（SEND_IF_COND）**：发送接口条件，检查SD卡版本（V2卡返回0x1AA），返回R1+4字节响应
5. **CMD55（APP_CMD）**：告诉SD卡下一条命令是应用特定命令（ACMD）
6. **ACMD41（SD_SEND_OP_COND）**：发送操作条件，HCS=1（支持高容量），循环发送直到R1=0x00（卡就绪），最多重试2048次
7. **CMD58（READ_OCR）**：读取OCR寄存器，确认卡的容量类型（CCS=1表示SDHC/SDXC，支持块寻址，CCS=0，SDSC（标准容量，字节寻址）。

**常用命令**：

| 命令 | 名称 | 功能 | 参数 |
|------|------|------|------|
| CMD0 | GO_IDLE_STATE | 复位 | 0 |
| CMD8 | SEND_IF_COND | 接口条件 | 0x000001AA |
| CMD17 | READ_SINGLE_BLOCK | 读单块 | 扇区地址（LBA） |
| CMD18 | READ_MULTIPLE_BLOCK | 读多块 | 起始扇区地址 |
| CMD12 | STOP_TRANSMISSION | 停止多块读 | 0 |
| CMD55 | APP_CMD | 应用命令前缀 | 0 |
| ACMD41 | SD_SEND_OP_COND | 操作条件 | HCS位 |
| CMD58 | READ_OCR | 读OCR | 0 |

**读扇区流程（CMD17）**：
1. 发送CMD17 + 4字节扇区地址 + 2字节CRC
2. 等待R1响应（0x00表示成功）
3. 等待数据令牌0xFE（最多等待几个毫秒）
4. 读取512字节数据
5. 读取2字节CRC（可以忽略）
6. 完成

**SDHC vs SDSC**：

- SDSC（标准容量，≤2GB）：字节寻址，CMD17参数是字节地址
- SDHC/SDXC（高容量，>2GB）：块寻址，CMD17参数是扇区号（LBA），每扇区512字节
- 完赛工程默认用SDHC（大部分TF卡都是SDHC）

### 2.5 sd_spi系列模块详解

完赛工程把SD卡SPI协议拆成**4个独立模块**，每个模块只做一件事：

[代码/图示块另行核对]

**模块1：sd_spi_init（初始化状态机）**

- 职责：执行完整的SD卡初始化流程（CMD0→CMD8→CMD55→ACMD41→CMD58）
- 状态：15个状态，包括上电延时、上电序列、每条命令的issue/wait
- 输出：init_done（初始化完成）、card_high_capacity（是否SDHC）、ocr（OCR寄存器值）、error_code（12种错误码）
- 关键参数：MAX_ACMD41_ATTEMPTS=2048（ACMD41最多重试2048次）

**模块2：sd_spi_command（命令发送器）**

- 职责：发送一条SD命令（6字节：命令号+4字节参数+1字节CRC），接收R1响应
- 接口：cmd_start（启动）、cmd_index（命令号0..63）、cmd_arg（4字节参数）、cmd_r1（R1响应）、cmd_busy（忙）
- 内部：调用sd_spi_byte_engine逐字节发送

**模块3：sd_spi_byte_engine（字节收发引擎）**

- 职责：SPI模式下收发一个字节（8个时钟周期）
- 接口：byte_start（启动）、byte_tx（发送字节）、byte_rx（接收字节）、byte_valid（接收完成）
- 实现：SPI时钟分频（默认4分频，100MHz系统时钟→25MHz SPI时钟），MOSI在时钟下降沿更新，MISO在时钟上升沿采样

**模块4：sd_spi_sector_reader（扇区读取器）**

- 职责：读取一个512字节扇区
- 接口：read_start（启动）、read_lba（扇区号）、read_data（输出数据）、read_valid（数据有效）、read_end（读取完成）、error_code
- 流程：发送CMD17→等R1→等数据令牌0xFE→读512字节→读CRC→完成
- 输出：每读一个字节就输出read_valid+read_data，上层可以流式处理

**为什么要拆成4个模块？**

1. **可复用**：sd_spi_command和sd_spi_byte_engine可以用在其他SD卡项目
2. **可测试**：每个模块可以单独写Testbench，不需要整个SD卡
3. **职责清晰**：初始化/命令/字节/扇区，每层只做一件事
4. **易调试**：出问题可以定位到具体模块（初始化失败？命令失败？字节收发失败？）

---## 三、从官方到FAT32的过渡思路

理解了FAT32基础之后，我们来看怎么从官方的"物理扇区扫描"过渡到"FAT32文件系统"。

### 3.1 整体架构替换

[代码/图示块另行核对]

**核心替换：用两个新模块+一个适配层替换bmp_read**

- `fat32_volume_scanner`（卷扫描器）：负责识别文件系统、解析BPB、扫描根目录、按文件名匹配PIC1~4.BMP，输出4个文件的起始簇号和文件大小，以及文件系统参数
- `fat32_file_streamer`（文件流读取器）：负责根据起始簇号和文件大小，通过FAT链遍历，读取文件的所有簇，输出文件字节流
- `sd_sector_adapter`（SD卡接口适配层）：把新模块的`sector_*`接口转换成官方`sd_card_top`的`sd_sec_*`接口（解决busy/byte_index/error信号缺失问题，详见第五节）

**上层保持不变**：sd_card_bmp的上层状态机（双缓冲、按键、自动轮播、显示切换）完全不变，只需要把原来bmp_read的接口适配到新的两个模块。

### 3.2 接口适配

**原来bmp_read的接口（扫描+加载一体）：**
- 扫描：scan_start、scan_start_sector、scan_max_sector、scan_target_count、scan_done、scan_found_valid、scan_found_sector、scan_found_total
- 加载：load_start、load_sector、bmp_data_wr_en、bmp_data
- 底层：sd_sec_read、sd_sec_read_addr、sd_sec_read_data、sd_sec_read_data_valid、sd_sec_read_end

**新架构的接口（扫描+加载分离）：**
- 卷扫描器：scan_start、scan_busy、scan_done、fs_error、partition_lba、sectors_per_cluster、fat_start_lba、data_start_lba、max_cluster、resource_valid[3:0]、resource0_cluster~resource3_cluster、resource0_size~resource3_size
- 文件流读取器：file_start、first_cluster、file_size、sectors_per_cluster、fat_start_lba、data_start_lba、max_cluster、file_busy、file_done、file_valid、file_byte、file_byte_offset、fs_error
- 底层（两个模块共用，经过适配层）：sector_req、sector_lba、sector_busy、sector_valid、sector_byte、sector_byte_index、sector_done、sector_error

**适配要点：**
1. 扫描阶段：原来的`scan_found_sector`（物理扇区号）变成`resourceX_cluster`（簇号）+`resourceX_size`（文件大小）。原来的`scan_found_valid`变成`resource_valid[X]`。从`img_sector0~3`改成`img_cluster0~3`加`img_size0~3`
2. 加载阶段：原来的`load_start + load_sector`变成`file_start + first_cluster + file_size`。原来的`bmp_data_wr_en + bmp_data`变成`file_valid + file_byte`（注意：原来一次输出24位RGB，新模块一次输出8位字节，需要在适配层把3个字节拼成24位RGB）。
3. 底层：原来的`sd_sec_read + sd_sec_read_addr + sd_sec_read_data...`变成统一的`sector_req + sector_lba + sector_busy + sector_valid + sector_byte + sector_byte_index + sector_done + sector_error`。两个新模块都需要读扇区，需要一个仲裁器（或者分时复用）。**关键：官方sd_card_top没有sector_busy和sector_byte_index信号，必须通过sd_sector_adapter适配层转换，不能直接对接。**
4. BMP头解析：原来bmp_read内部解析BMP头，现在文件流读取器只输出原始字节流，BMP头解析需要移到适配层（sd_card_bmp内部）。

### 3.3 文件名约定

仍然使用固定文件名`PIC1.BMP`、`PIC2.BMP`、`PIC3.BMP`、`PIC4.BMP`（8.3格式，大写字母），但现在是通过**目录项匹配**找到文件，而不是物理扇区扫描。

用户需要做的：把4张BMP图片命名为`PIC1.BMP`~`PIC4.BMP`，放在TF卡的**根目录**下。

> 注意：FAT32的长文件名（LFN）在目录项里是用多个32字节条目存储的，Unicode编码。完赛工程的扫描器只匹配8.3短文件名（大写），不支持长文件名。如果用户在Windows上拷文件，Windows可能会自动生成短文件名（比如`PIC1~1.BMP`），这时候匹配会失败。建议用户在格式化TF卡时选择FAT32，并且确保文件名是大写的8.3格式，或者在扫描器里增加长文件名支持（进阶内容，本节课不涉及）。

但更关键的是：**完赛工程的两个FAT32模块使用的是`sector_*`接口，而官方sd_card_top使用的是`sd_sec_*`接口，这两个接口不匹配，不能直接对接！** 具体来说：

- 新模块需要`sector_busy`信号（表示SD卡正在读），但官方sd_card_top没有busy信号
- 新模块需要`sector_byte_index`信号（当前读到扇区的第几个字节，0~511），但官方sd_card_top不输出字节索引
- 新模块有`sector_error`信号（错误码），但官方sd_card_top没有错误输出



### 3.4 最小改动方案

**只替换sd_card_bmp内部的bmp_read，上层状态机保持不变。**

具体来说：
1. 新增三个文件：`fat32_volume_scanner.v`、`fat32_file_streamer.v`、`sd_sector_adapter.v`
   - 前两个是完赛工程的FAT32核心模块，代码可以参考完赛工程，但**不能直接拷过来就用**——因为它们的扇区读接口（sector_*）跟官方sd_card_top的接口（sd_sec_*）不匹配，必须通过sd_sector_adapter适配层转换
   - 第三个是本节课新增的接口适配层，需要自己写（代码见第五节）
2. 修改`sd_card_bmp.v`：
   - 删除bmp_read实例
   - 新增fat32_volume_scanner实例和fat32_file_streamer实例
   - 新增sd_sector_adapter实例（对接官方sd_card_top）
   - 新增扇区读仲裁逻辑（两个模块都要读SD卡，分时复用）
   - 新增BMP头解析逻辑（从文件字节流里解析BMP头，提取宽高和像素数据）
   - 新增字节到RGB的拼装逻辑（file_byte是8位，需要3个字节拼成24位RGB）
   - 上层状态机（双缓冲、按键、自动轮播）保持不变
3. 顶层`top_tf_hdmi_audio.v`：sd_card_bmp的外部接口不变，不需要修改

这个方案的好处是改动范围可控，只动sd_card_bmp内部，上层和顶层都不用改。风险也比较小——如果新模块有问题，可以随时换回bmp_read。

我们来看完赛工程的两个核心模块是怎么实现的。

### 4.1 fat32_volume_scanner（卷扫描器）

**功能**：识别FAT32文件系统，解析BPB，扫描根目录，匹配PIC1~4.BMP，输出文件起始簇号和文件大小。

**12状态状态机：**

[代码/图示块另行核对]

> **图例：** 绿色=正常完成状态(FINISH)；错误转移统一标注"错误"，详细错误码包括：扇区读错、无引导签名(0x55AA)、不支持的分区类型、BPB校验失败、资源缺失(4张BMP未全部找到)。

**关键流程：**

1. **读LBA0**：读TF卡的第一个扇区，判断是直接FAT32引导扇区还是MBR
   - 如果第0字节是`0xEB`或`0xE9`（跳转指令），说明是直接引导扇区，partition_lba=0
   - 如果偏移450的分区类型是`0x0B`或`0x0C`，说明是MBR，从偏移454读分区起始扇区作为partition_lba
   - 最后两个字节必须是`0x55 0xAA`（引导签名），否则报错

2. **解析BPB**：从引导扇区解析文件系统参数
   - 校验：每扇区512字节、每簇扇区数是2的幂、保留扇区数非零、FAT表数量是1或2、根目录簇号≥2
   - 输出：sectors_per_cluster、fat_start_lba、data_start_lba、max_cluster

3. **扫描根目录**：读根目录的第一个簇（簇2），逐个32字节目录项扫描
   - 匹配文件名：`PIC1    BMP`、`PIC2    BMP`、`PIC3    BMP`、`PIC4    BMP`（8字节文件名+3字节扩展名，不足补空格）
   - 匹配成功后，从目录项提取起始簇号（偏移20高16位+偏移26低16位）和文件大小（偏移28，4字节）
   - 4个文件都找到后（resource_valid==4'hf），扫描完成

> **局限说明**：完赛工程的卷扫描器只读根目录的**第一个簇**（簇2）。如果根目录项很多超过一个簇（通常每簇8扇区=4KB=128个目录项），后面的目录项就扫不到了。对于只有4个BMP文件的场景来说完全够用，但如果根目录放了很多文件，建议把PIC1~4.BMP放在根目录的前面，或者扩展扫描器支持多簇根目录遍历。

**错误码：**
- `ERR_SECTOR (0x10)`：扇区读错误
- `ERR_BOOT_SIGNATURE (0x20)`：引导签名错误（不是0x55AA）
- `ERR_UNSUPPORTED_BPB (0x21)`：BPB参数不支持
- `ERR_RESOURCE_MISSING (0x22)`：根目录里找不到PIC1~4.BMP

### 4.2 fat32_file_streamer（文件流读取器）

**功能**：根据起始簇号和文件大小，通过FAT链遍历，读取文件的所有簇，输出文件字节流。

**7状态状态机：**

[代码/图示块另行核对]

**关键流程：**

1. **读数据簇**：从first_cluster开始，计算簇的起始扇区（`data_start_lba + (cluster-2)*sectors_per_cluster`），逐个扇区读取
   - 每个扇区的512字节通过`file_valid + file_byte + file_byte_offset`输出
   - `remaining_bytes`计数器记录还剩多少字节，减到0表示文件读完

2. **读FAT表找下一簇**：当前簇的所有扇区读完后，去FAT表查这个簇对应的FAT条目
   - FAT扇区号：`fat_start_lba + (cluster >> 7)`（每个扇区128个条目）
   - FAT条目偏移：`(cluster & 0x7F) << 2`（每个条目4字节）
   - 读FAT扇区，提取对应偏移的4字节，得到下一个簇号

3. **判断下一簇**：
   - 如果是`0x0FFFFFF8 ~ 0x0FFFFFFF`：文件结束（EOF），正常完成
   - 如果是`0x00000000`：空闲簇，说明FAT链断了（提前EOF错误）
   - 如果簇号<2或>max_cluster：簇号越界错误
   - 如果下一簇==当前簇：FAT环错误（自己指向自己）
   - 如果遍历簇数超过MAX_VISITED_CLUSTERS（默认8192）：遍历超限错误（防止FAT环导致无限循环）
   - 否则：跳到下一簇，继续读数据

**错误码：**
- `ERR_SECTOR (0x10)`：扇区读错误
- `ERR_FAT_LOOP (0x23)`：FAT环（下一簇==当前簇，或final_chain_check时不是EOF）
- `ERR_CLUSTER_RANGE (0x24)`：簇号越界
- `ERR_EARLY_EOF (0x25)`：提前到文件尾（还没读完file_size就遇到EOF）
- `ERR_VISITED_EXHAUSTED (0x26)`：遍历簇数超过MAX_VISITED_CLUSTERS

### 4.3 两个模块的协作关系

[代码/图示块另行核对]

1. 先调用卷扫描器，识别文件系统，找到4个文件的起始簇号和大小
2. 加载图片时，调用文件流读取器，传入起始簇号和文件大小
3. 文件流读取器通过FAT链遍历，输出文件字节流
4. 适配层从字节流里解析BMP头，提取像素数据，送到SDRAM

**注意**：两个FAT32模块都不直接对接sd_card_top，而是通过sd_sector_adapter适配层中转。适配层负责把新模块的sector_*接口转换成官方sd_card_top的sd_sec_*接口，并且自己生成sector_busy和sector_byte_index信号。

## 九、文件系统设计的核心原则

1. **认识文件系统，不要绕过它**：TF卡是有文件系统的，不要直接读物理扇区。通过目录项找文件、通过FAT链读文件，才是正确的做法。绕过文件系统（靠魔数扫描）虽然简单，但局限太多，迟早出问题。

2. **FAT链是碎片化的解决方案**：文件不连续存放是常态，不是异常。FAT链就是用来解决碎片化问题的——不管文件的簇怎么分散，FAT链都能按顺序把它们串起来。设计文件读取时必须支持FAT链，不能假设文件连续。

3. **参数从BPB动态读取，不要硬编码**：不同TF卡的每簇扇区数、FAT表大小、保留扇区数都可能不一样。必须从引导扇区的BPB动态读取这些参数，不能硬编码。硬编码的话换一张卡就可能不工作。

4. **支持MBR和直接引导两种格式**：有的TF卡有MBR分区表，有的没有（超级软盘格式）。必须两种都支持，先读LBA0判断是哪种格式，再找到FAT32分区的起始位置。

5. **错误处理要完善**：文件系统操作可能遇到各种错误（扇区读错、引导签名错、BPB不支持、文件找不到、FAT环、簇越界、提前EOF）。每个错误都要有明确的错误码，系统不能卡死，要能报错并恢复。

6. **防无限循环**：FAT表可能损坏，出现FAT环（簇A指向簇B，簇B又指向簇A）。必须有遍历簇数上限（MAX_VISITED_CLUSTERS），超过上限就报错，防止无限循环导致系统卡死。

7. **接口适配要隔离**：新模块的接口跟旧驱动不匹配时，不要修改旧驱动（尤其是官方提供的底层驱动），而是写一个适配层做接口转换。这样旧驱动保持稳定，新模块也能正常工作，出问题时容易定位是适配层的问题还是新模块的问题。
