## 图2-1提示词

生成一张中文工程论文用系统框图，横版16:9、白底、扁平矢量风格、深蓝文字、整齐圆角矩形和正交箭头，字体清晰，留足空白，无装饰性电路背景、无立体效果。标题：“图2-1 梯间守望系统整体硬件拓扑与数据流/控制流框图”。图内精简文字，严格按以下真实架构绘制，不凭空增添模块。

中心大虚线框标“安路 EG4S20BG256 FPGA硬件逻辑”，框外左侧TF卡、底部PC和按键拨码、右侧显示器。框内上方是从左向右的主数据通路，必要时分两行但保持阅读方向：
TF卡（FAT32 / RGB24 BMP）→ SPI读卡与FAT32文件解析 → BMP解码与可选2×2均值缩小 → CDC写入桥 → SDRAM访问子系统 → 帧读取与预取FIFO → 亮度/对比度与转场 → 图层叠加 → HDMI音视频桥 → TMDS PHY → 显示器。显示器标注“640×480 HDMI”。解码模块小字“640×480直通；1280×960缩小”。注意缩小在写入SDRAM之前，绝不能画到SDRAM之后。

SDRAM访问子系统用浅蓝组框，含“三路突发仲裁器”“SDRAM控制器”“SDRAM图像缓存”。仲裁器与控制器相连，控制器与存储双向连接。显示三路客户端：CDC图像写入、视频帧读取、缩略图缓存构建。旁注“视频低水位优先；后台写入与缓存交替；完整突发事务”。缩略图构建从该子系统读取并连接缩略图缓存，缓存连接图层叠加。不标乒乓仲裁，不把缩略图画为所有视频像素必经的串行模块。

图层叠加框内列“中文OSD / 字幕 / 参数菜单 / 缩略图 / PCM时域波形”。下方音频支路：“48 kHz合成音调与应急提示音”→ HDMI音视频桥；从HDMI音视频桥拉出箭头标“最终输出PCM抽头”到“时域波形绘制”，再到图层叠加。不是FFT，也不是TF音乐解码。

下方控制区域：按键/拨码 → 消抖与交互控制 → 播放/参数控制；SW4单独接“双源告警与应急状态机”；PC ↔ UART接入与事件上报 ↔ 应急状态机，PC标注“演示楼层 / 查询 / 事件 / 人工ACK”。用户参数Flash ↔ 参数控制。控制虚线分别连视频播放、图层叠加、声音选择。应急状态机小字“告警优先PIC5；ACK仅接收确认；全部来源解除后恢复”。

最下方窄条标“时钟与复位：50 MHz系统域 / 40 MHz内存域 / 25 MHz像素域 / 125 MHz串化域；CDC与帧边界配置提交”。图例：蓝色实线=图像数据，紫色实线=音频/PCM，橙色虚线=控制，青色双向线=UART。走线不穿文字，分支连接用清晰圆点，箭头方向准确。不写云端、真实电梯控制、安全加密、实测延迟或功耗。

## 图2-3提示词

生成与图2-1风格统一的中文工程论文软硬件协同架构图，3840×2160横版16:9，纯白背景，深蓝正文，浅蓝硬件组框、浅青软件组框、橙色控制箭头，扁平矢量、清晰正交走线、足够字号与空白。标题：“图2-3 FPGA硬件逻辑与PC监控上位机软件协同架构图”。不要绘制仿真的应用窗口，不画电梯安全控制回路或云平台。

版面分左右两大边界框，中间为双向串口：左“FPGA硬件终端”，右“PC监控上位机：Python / Tkinter”。必须写Tkinter，不是PyQt6。

左框按层组织：①UART RX → 会话/序号/CRC校验 → 命令解析与分发；命令分支有“FLOOR：演示楼层/方向/门状态”“ALERT：串口告警源”“ACK：事件编号确认”“SUB与只读查询”。②中心“告警与事件状态控制”，并接“SW4本地告警源”与“串口告警源”，以OR来源合成触发；旁接“演示状态寄存器”和“字幕/查询状态”。③输出至“显示与声音控制：日常PIC1～4 / 应急PIC5 / 中文状态 / 提示音”，并至“事件编号 / 状态上报 / 有限重发” → CRC封装 → UART TX。UART RX与TX各接中间串口链路。

右框按层组织：底层“transport.py：真实串口传输”，其上“protocol.py：帧封装、解析与CRC校验”，其上“core.py：会话、设备状态、事件与命令调度”。core分别连接“ui.py：状态看板 / 楼层演示 / 事件时间线 / 人工ACK”“journal.py：事件日志与历史回放”。界面旁有操作者小图标，箭头“人工确认”进入ACK命令路径。右下角小框注明“SIM/回放用于演练，与真实串口证据区分”。PC不参与FPGA像素渲染。

中间串口通道清楚分两条独立方向：PC→FPGA橙色箭头“HELLO会话 / FLOOR / ALERT / ACK / SUB / 查询”；FPGA→PC蓝色箭头“RESCUE事件+CRC / 状态回读 / 启动里程碑”。连接标“UART 115200 bit/s，8N1”。旁注“写帧：会话号 + 序号 + 负载 + CRC16”；“CRC用于完整性校验，不是加密认证”。不能把会话号画在RESCUE上行事件里。

图下方独立浅灰横带绘制编号交互流程，7步从左向右：①告警触发 → ②应急显示与事件上报 → ③PC校验并展示 → ④人工发送匹配ID的ACK → ⑤FPGA回读ACKED → ⑥所有有效告警源解除 → ⑦恢复日常显示。⑤下方醒目标注“ACKED仍保持告警提示”。另以细分支表示“未确认：约1秒等待、最多重发2次 → TIMEOUT”，TIMEOUT旁注“匹配迟到ACK仍可被接受”。底部文字“楼层为演示输入；ACK仅表示接收确认，不表示故障解除或救援到场”。不将该横带画成同步软件调用栈。

确保双向通信、命令解析、事件回传和人工确认关系清楚，每条线只接对应节点。不要用密集的代码段、过长源文件名或无关图标填满图面。
